# judgment-gates — 确定流程还是自主判断

本文件是 `judgment` 的细则之一。它只提供**判断层的门槛**；凡涉及阈值、流程、安全边界的部分，一律以 owner 文档为准（见每节末尾的"归谁管"）。

## 1. 为什么先问这一句

把确定性任务交给自主判断，代价是**不稳定 + 成本**（每次跑的路径可能不同）；把开放性任务塞进写死的流程，代价是**做不对**（流程编不出该有的取舍）。

两种错误不对称：前者是"贵而飘"，后者是"便宜而错"。所以门槛要设在**任务是否能在执行前被完整写全**这一点上，而不是设在"这事儿难不难"上。

## 2. 三个判别问题

按顺序问，任一条落入"确定性"即走流程，不必再问下去。

1. **步骤可枚举吗？** 能否在执行前把 1..N 步写全，且中途不需要看结果再决定下一步？
2. **输入已知吗？** 每步需要的输入在开始前就存在（文件、参数、接口），不需要临场取回再判断？
3. **失败可穷举吗？** 可能的失败模式能列完，且每一种都有确定的处理分支？

三条全"是" → 确定流程（脚本、有序命令、单条工具调用）。
任一条"否" → 进入第 3 节做开放性分级。

## 3. 任务开放性分级（它决定要花多少判断预算）

| 级别 | 特征 | 判断预算 | 该做什么 |
|---|---|---|---|
| L0 闭合 | 步骤、输入、失败全已知 | 0 | 直接编排，不加载本技能 |
| L1 单点未知 | 只有一处需要取舍（选哪个方案/哪个文件） | 小：一次比较 | 自己决定 + 记录理由，不必问人 |
| L2 多点未知 | 多处取值相互依赖 | 中：先列决策点再逐个定 | 先写计划，再动手；决策点交用户裁 |
| L3 开放 | 目标本身需要澄清，或范围会自己长 | 大：先定边界再谈做法 | 停下来问边界；问完再分级重估 |

分级的目的不是分类学，而是**决定你在哪一级该停手**：L2 以上不停手就开始写，通常等于把返工留给了下一步。

## 4. 与规划技能的交接

本仓库有五个规划技能（`create-a-small-plan` / `create-a-plan` / `create-a-big-plan` / `diagnose-before-plan` / `reference-before-plan`）。交接规则：

- **在 dsh-plans 预设内（智能规划模式 / 有限元机器学习模式 / 机器学习规划模式），凡改动仓库一律走规划技能**：persona 的 "The planning workflow always applies" 与执行交接门**不可被本技能绕过**。本技能在这里**只决定规划到多深**，不决定要不要走流程。
- 分级 → 技能：L0/L1 → `create-a-small-plan`；L2 → `create-a-plan`；L3 → `create-a-big-plan`。
- 只有在**不使用 dsh-plans 工作流**的环境里，"要不要规划"才由本技能决定；所在预设若声明规划工作流常驻，一律以预设为优先。
- 出现故障而非改动 → `diagnose-before-plan`，先定位根因再谈改法（**只压症状不算修好**）。
- 需要外部事实（库行为、协议语义、兼容性）才能定分级 → `reference-before-plan`。

**规划深度本身归规划技能定义**（例如各技能对提问数量的要求），本文件不复述、不覆盖。

## 5. 反过来：什么时候该从流程退回判断

即使一开始判为确定流程，出现下列任一情形应**升一级**重新判断，而不是继续硬跑：

- 同一分支连续失败，说明"失败可穷举"这个前提已经不成立。
- 出现了流程里没有的输入形态（新格式、新编码、跨平台差异）。
- 需要做不可逆操作，而流程里没有对应的确认点。

升一级的代价远小于在错误层级上硬推。
