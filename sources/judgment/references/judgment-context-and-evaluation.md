# judgment-context-and-evaluation — 上下文预算与"好不好"的口径

本文件是 `judgment` 的细则之一。上下文**阈值与外化/压缩时机**归 `context-handoff`（**仅当本预设提供该文档时**；不提供时按 `SKILL.md` 的停止与上报格式处理，**不得自定阈值**）；本文件只给"外化之后，上下文里丢什么、留什么"的优先级与评估口径。

## 1. 上下文：先外化，再压缩，最后才丢

直接截断是最差的选项：它按时间顺序丢，而时间顺序与重要性无关——最先丢掉的往往正是任务开始时定下的目标。

顺序是固定的：**先按 `context-handoff` 外化 → 再压缩摘要 → 再按优先级腾位 → 最后才考虑丢**。外化在前是 owner 文档的硬要求（"externalise before compaction, not after"），本文件不改变该顺序，只说清外化之后上下文里该留什么。

## 2. 保留优先级（从必保到可丢）

| 等级 | 内容 | 处置 |
|---|---|---|
| **P0 必保** | 用户目标与约束（要什么、不要什么、边界在哪） | 永不丢；每次压缩后复述一遍 |
| **P0 必保** | 历史**结论**（已定的事、已排除的方案及原因） | **原文已按 `context-handoff` 逐字落盘后**，上下文里压成一句结论，保留"为什么排除" |
| **P0 必保** | 当前子任务的输入与可回滚点 | 保留到该子任务结束 |
| **P1 可压缩** | 已完成的步骤过程（做了什么、为什么这么做） | 压成一行事实，丢掉中间输出 |
| **P2 可丢** | 过程流水账、重复的读文件内容、已被结论吸收的探测输出 | 可直接丢 |
| **P3 必须先落盘再丢** | 一次性、不可重建的原文（探测结果、报错全文、哈希） | 先写进工件再丢 |

判据：**丢了它，下一步还能不能做出同样的决定？** 能 → 可丢；不能 → 必保或先落盘。

## 3. 丢失等级与代价

- 丢 P2：无代价。
- 丢 P1：会略微降低可解释性，但结论仍在。
- 丢 P0：等于换了一个任务在做，后续所有决定都失去依据——这是最常见的"越做越偏"的成因。
- 丢 P3：不可恢复，只能重跑。

## 4. 评估一个 Agent：三个口径

只看任务完成率的评估会选出"什么都敢做"的 Agent。至少要三个口径一起看：

1. **完成率**：该做完的做完了吗。
2. **越界行动率**：**不该行动时行动了**多少次（做了没被要求的事、动了不该动的范围、在信息不足时下结论）。这一项必须单独计数，因为它不会体现在完成率里。
3. **过度复杂化率**：把简单问题做复杂的次数（该一步解决的用了五步、该改一行的重构了一棵树、本该说"不需要"的做了一整套）。

补充两条纪律：

- 三个口径必须**按任务类型分组**比较。探索性任务天然多步，用同一把尺子量会得出反直觉的结论。
- **"正确地什么都没做"是成功**，不是零分。评估表里要给这种结果留位置。

## 5. 多智能体：先算沟通成本

多智能体不是"更强"，是"把一件事拆给多个上下文"。它只在一种情况下划算：

> 任务能拆成**独立且可并行**的小块，且块之间几乎不需要对齐。

拆之前先估三项沟通成本：

- **交接损耗**：每个子代理都要重新建立上下文，重复读同样的材料。
- **口径漂移**：同一概念在不同子代理手里变成不同含义，最后结果对不上。
- **合并成本**：结果回来要人去合并、去重、消解冲突——这部分往往是纯增加的工作。

判据：**净收益 = 并行加速 − (交接损耗 + 口径漂移 + 合并成本)**。估不出正值就不要拆；拆了之后再对齐，成本已经付掉了。

反例：子任务彼此依赖、需要频繁同步、或最终产物是一份必须前后一致的文档——这些情况下拆开只会更慢更乱。
