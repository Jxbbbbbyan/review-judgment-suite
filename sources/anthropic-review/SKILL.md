# Anthropic 分层代码审查（自审版）

目标：把能由机器发现的问题在提交前就解决掉，只把真正需要人的判断留给人。每一步都要做，不能跳过或合并。

## 0. 收集输入
- 本次改动的 diff（git 仓库用 git diff；不是 git 仓库就列出改动文件和改动内容）。
- 改动意图：要解决什么问题；如果是修 bug，症状是什么。
- 项目约定文件：AGENTS.md、CLAUDE.md、REVIEW.md，有就必须读并遵守。
- 当前是第几轮，以及之前各轮的审查发现。

## 1. 先验证，不靠口头
- 实际运行能证明改动正确的检查：测试、构建、lint、类型检查，或复现原问题的命令，并记录真实输出。
- 没有可运行的检查时，就补一个最小的测试或复现脚本，不能只说“完成了”。

## 2. 风险分级（由改动内容决定）
- Low：文档、文案、仅内部功能、开关后面的纯新增。
- Medium：普通功能改动；缓存、自动更新、系统提示词等敏感区域。需要 1 人审批。
- High：最高风险代码。需要 2 人审批。
- 认证、计费、CI/工作流、发布与安装脚本、自动更新器，以及 REVIEW.md 里列为敏感的路径，永远至少需要一个人看。
- 再独立判断一次：即使分级说不需要人，这个具体改动是否仍该让人看？写出理由。
- AI 的通过不能顶替必需的人工审批。

## 3. 用全新上下文分头找问题
能开子 agent 就开，每个都只拿 diff、意图和约定文件，不带写代码时的思路：
- 正确性：是否解决了声明的问题？是否契合现有系统？是否弄坏了别处？修 bug 要找根因，不能只压住症状。
- 安全：注入、鉴权绕过、密钥泄露、不安全的反序列化、权限放大、依赖风险。
- 端到端行为：从使用者角度推演改动后的实际行为。
- 约定：是否违反 AGENTS.md/CLAUDE.md/REVIEW.md，是否让这些文件里的某一行变得过时。
深度按风险：Low 快速过，Medium 标准，High 深入。

## 4. 复核后才算数
- 每条候选问题再独立复核一次，确认是真问题才保留。
- 必须给出“文件:行号”作为证据，不能凭名字猜。
- 只关于风格、诊断或清理的丢掉。
- 打标签：Important（本次引入、必须修）、Nit（小问题，最多 3 条）、Pre-existing（改动前就有，不算本次的错）。
- 同一类问题出现多处时，标为“这一类问题”，全部修掉。

## 5. 修复与收敛
- 所有 Important 修掉，或写明不修的理由；修完重跑第 1 步的检查。
- 不重复已经处理过的问题；第 3 轮起只看新改动。
- 自审超过 3 轮仍有 Important：停止修补，退一步重新考虑方案，并告诉用户。

## 6. 输出
第一行写数量，例如“发现 2 个 Important、1 个 Nit、0 个 Pre-existing”，或明确写“没有需要修的问题”。然后依次写：
1. 结论：可提交审查 / 修后再审 / 需要人看。
2. 风险等级、理由，以及需要几个人审批。
3. 问题列表：标签、文件:行号、问题、原因、修法、处理结果。
4. 第 1 步实际跑过的命令和结果。
5. 这次审查覆盖不到、需要人判断的点（方向是否该做、会被别人照抄的架构、高风险代码）。
这份输出的要点要写进提交审查时的 -Notes（测试方式、风险、如何回滚、请重点看）。
